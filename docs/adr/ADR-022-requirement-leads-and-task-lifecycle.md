# ADR-022：需求负责人、执行人和统一任务生命周期

- 状态：Accepted
- 日期：2026-09-21
- 依据：本次用户确认的需求流转与子任务改造。
- 相关：替代 ADR-021 第 6 条中暂不允许领域管理员分配需求参与人的阶段限制；不改变公司成员治理和最终部署审批。

## 范围与决策

本次明确跨越人员授权及会话 12–16、24、26、28–31 的既有交付流程，统一修改服务端、Web 和受控 Tool 入口。公司事实来源、认证与部署拓扑保持现有边界。

1. 一个需求有产品、UX、开发、测试四名领域负责人，候选人必须具有对应领域管理员角色。产品关联负责人，各负责人维护本领域执行人；同一成员可在有对应角色时兼任负责人和执行人。全局治理角色不自动获得需求内负责人身份。
2. 进入评审前，四个领域均需具备负责人及至少一名有效执行人。需求待审核由产品负责人审核；待评审开始后，四个领域分别留下通过记录，全部通过才进入 UX 待设计。驳回回到草稿，重新评审不得复用旧结论。评审开始后冻结人员关联，避免审核人与执行范围漂移。
3. 需求生命周期：草稿 → 需求待审核 → 待评审 → 评审中 → UX待设计 → UX设计中 → UX待审核 → 待开发 → 开发中 → 待测试 → 测试中 → 验证修复中 → 验收中 → 待发布 → 发布完成。需求或评审驳回到草稿，UX审核驳回到UX设计中。不再提供跳过UX的流程出口。
4. UX、开发、测试负责人分别在 UX待设计、待开发、待测试阶段，为本领域已关联执行人手动创建任务；不自动创建UX任务。开始阶段前必须有对应任务。
5. 设计、开发、测试、缺陷共用五种任务状态：待处理、进行中、阻塞中、待验证、已完成。执行人处理并提交待验证，领域负责人审核；缺陷由开发执行人修复，由该需求测试人员验证。验证失败回到进行中。任务阻塞与恢复必须记录原因。
6. 测试人员可在测试中创建缺陷并指定需求开发执行人。开发人员可立即修复，缺陷出现在开发任务面板和任务看板。全部用例执行完毕才能进入验证修复；存在未执行、执行中、阻塞或跳过用例时不得进入。全部用例通过且无未完成缺陷可直接进入验收。验收由产品负责人确认后进入待发布。
7. 角色权限码与需求内负责人/执行人身份必须同时满足。Web、REST、GitLab应用服务及Agent Tool复用同一授权和状态规则；看板位置不得覆盖真实状态，不能拖拽绕过审核。

## 一致性与数据库

负责人沿用 requirement_participants；执行人和本轮评审票新增公司作用域表。所有人员调整、评审票与状态流转串行锁定需求聚合；每次流转继续使用版本与幂等键，事件和状态原子写入。不得在持锁事务中调用GitLab等外部服务。

以新Flyway迁移转换既有任务状态，保留历史事件，不回改已发布迁移。新建任务必须关联需求和执行人。已存在的无负责人或无执行人的需求需补齐关联后才能继续推进。

## 验证要求

覆盖四方会签、旧票失效、缺失人员阻断、非负责人越权、任务待验证与驳回、阻塞恢复、缺陷修复并行、未跑完用例不得提前进入验证修复、真实看板状态以及REST/Tool一致性。
