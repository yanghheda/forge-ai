# ADR-001：采用模块化单体而非业务微服务

- 状态：Accepted
- 日期：2026-09-02

## 上下文

ForgeAI 需要覆盖 Product、UX、Development、QA 和 Release 的完整交付链，但 MVP 由小团队或单人开发维护。工作流、权限、审计和交付资产之间存在大量需要一致演进的业务规则。过早拆分业务微服务会引入分布式事务、服务发现、跨服务契约和部署运维成本，削弱纵向交付速度。

Monorepo 并不意味着所有代码没有边界。后端仍需要清晰的业务模块、依赖方向与公开应用服务。

## 决策

`forge-server` 采用 Spring Boot 模块化单体。业务模块内部遵循 `controller/infrastructure → application → domain` 的依赖方向；Repository 实现依赖领域端口。跨模块写入通过目标模块的公开应用服务或领域事件完成，不直接访问对方 Repository。

Web、Server 和 Agent 仍是三个独立应用，共同保存在 Monorepo 中。

## 后果

- 单次业务命令可以使用一个本地数据库事务维护核心不变量。
- 部署、调试和本地开发复杂度较低，适合 MVP 与自托管。
- 必须以架构测试和代码评审防止模块边界退化。
- 单体进程的故障和扩缩容粒度较粗；只有出现经验证的独立扩缩容或隔离需求时才考虑拆分。

## 替代方案

- 业务微服务：暂不采用，因为当前收益不足以覆盖分布式一致性和运维成本。
- 无模块分层的传统单体：不采用，因为会导致跨领域耦合和 Repository 任意访问。
