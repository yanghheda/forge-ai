# 会话 13：文档不可变版本与 Tiptap 编辑器

## 本轮边界

完成 PRD 元数据、不可变正文版本、指定版本发布和版本历史的服务端契约，以及 Tiptap 编辑器的本地草稿隔离。附件上传和 Qdrant 索引消费者不在本轮实现范围内。

## 关键取舍

- `documents` 只保存元数据、当前版本指针和乐观锁；正文只追加到 `document_versions`，因此历史版本没有更新 API。
- 显式保存才创建服务端版本；自动保存仅写浏览器 LocalStorage，避免把每次输入都变成难以阅读的审计版本。
- 保存版本与切换 `current_version_id` 在一个事务；发布版本、状态更新和 `DOCUMENT_VERSION_PUBLISHED` Outbox 也在一个事务。索引执行由后续会话的消费者处理。
- 浏览器草稿键为 `forge:document-draft:{userId}:{documentId}:{baseVersion}`。版本变动后新草稿不会覆盖旧基线，UI 要求用户查看差异、复制或丢弃。

## 验证

- `DocumentContentTest`：ProseMirror JSON 规范化为纯文本并生成 64 位 SHA-256。
- `local-draft.test.ts`：草稿按用户、文档和基线版本隔离。
- Flyway 集成测试：V9 在真实 MySQL 上成功迁移（需要 Docker）。

## 风险与后续

- 当前 API 尚未接入工作项详情页；会话 14 的 Product 纵向切片应把 PRD Tab 接到页面并补 HTTP 并发保存、发布不存在版本和旧版可读的集成测试。
- 当前 Outbox 只生产，不消费；Qdrant 不可用不应影响文档 CRUD。
- 正文哈希标识规范化文本相等，但不能替代乐观锁：它不能表达“用户基于哪个元数据版本保存”。

## 复盘问题

1. 为什么自动保存不直接生成服务端版本？
2. 内容 hash 能证明什么，又不能替代哪些并发控制？
3. 为什么发布事务写 Outbox，而不是在事务中直接调用索引服务？

1. 自动保存不直接生成服务端版本，是因为编辑过程会产生大量细碎、不可读的中间状态。不可变版本应代表用户明确确认的成果，便于历史查看、发布、审计和后续引用；自动保存仅用于防止浏览器崩溃或误关闭丢稿。
2. 内容 hash 能证明规范化后的正文内容是否相同，可用于去重、检索一致性校验和发现内容被篡改。它不能替代乐观锁：两个用户可能基于不同的文档元数据版本保存出不同内容，hash 无法表达“这次写入基于哪个版本”，也无法防止后写覆盖先写。expectedVersion 才负责检测并发修改和拒绝陈旧写入。
3. 发布事务写 Outbox，是为了把“文档发布成功”和“需要索引”可靠地绑定在同一数据库事务中。若直接调用索引服务：索引成功但事务回滚会产生幽灵索引；事务提交成功但网络超时又可能漏索引；同时外部调用会拉长持锁时间。Outbox 让发布先原子落库，再由异步消费者按可重试、可观测的方式索引。
