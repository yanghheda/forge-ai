我选了一条“创建 Project”的真实写请求链；它落到 MySQL，不涉及外部系统：

`POST /api/v1/projects`
→ `CsrfConfiguration.csrfFilterRegistration()` 先验证 `X-CSRF-TOKEN`
→ `AuthenticationFilter.doFilterInternal()` 从服务端 Session 恢复 `AuthContext(userId)`
→ `ProjectController.create()`
→ `ProjectCommandService.create()`
→ `PermissionEvaluator.requireWorkspace(userId, workspaceId, "project.manage")`
→ `MybatisPermissionStore.findWorkspacePermissionSet()` / `PermissionMapper.workspacePermissions()`
→ `MybatisProjectStore.createWithCreatorMembership()`（事务）
→ `ProjectMapper.insertProject()`、`lastInsertId()`、`insertCreatorMember()`，最后用 `findByIdAndWorkspaceId()` 回读。

这里的关键不是前端传的 `workspaceId` 被“相信”，而是它与 Session 中的 `userId` 一起进入服务端授权 SQL，并且项目读回也携带 `projectId + workspaceId`。

本阶段最重要的三个不变量：

1. **首个管理员初始化只能成功一次，而且身份图不能半完成。**  
   `MybatisPlusInstanceBootstrapStore.create()` 用事务包住全部写入，并通过 `InstanceBootstrapMapper.lockAndGetInitializedAt()` 锁定单例设置行；`markInitialized()` 必须更新一行。  
   `InstanceBootstrapIntegrationTest.serializesConcurrentInitializationSoExactlyOneSucceeds()` 验证并发时恰好一个 `201`、一个 `409`；`rollsBackEveryFactWhenMidTransactionWriteFails()` 验证中途失败不残留用户、Workspace 或角色事实。

2. **浏览器的 Cookie 不是授权结论；修改请求必须同时具备有效 Session 与其绑定的 CSRF Token。**  
   `AuthenticationFilter.doFilterInternal()` 只从 Session 中建立请求级 `AuthContext`，并实施绝对过期；`CsrfConfiguration` 以 `HttpSessionCsrfTokenRepository` 验证修改请求。登录还在 `AuthController.login()` 中调用 `changeSessionId()`。  
   `CsrfIntegrationTest` 覆盖无 Token/错误 Token 的拒绝；`AuthenticationIntegrationTest.logoutRevokesOnlyCurrentConcurrentSession()` 和 Session 过期集成测试覆盖服务端撤销与过期失效。

3. **任何 Project 操作都不得跨 Workspace 泄漏，成员撤销后访问必须立刻失效。**  
   `ProjectQueryService.get()` 先验 Workspace 成员关系，再执行 `findByIdAndWorkspaceId(projectId, workspaceId)`，随后检查项目权限；写路径同样在 `ProjectCommandService` 和 `PermissionEvaluator` 重复校验。`ProjectMapper` 的资源查询与更新均显式带 `workspace_id`。  
   数据库层还有 `projects(workspace_id, key)` 唯一约束，以及 `project_members` 对 `(workspace_id, user_id)` 的外键约束。`WorkspaceProjectScopeIntegrationTest` 覆盖已知跨 Workspace ID 的读/归档均为 `404`，并覆盖移除项目成员或 Workspace 成员后访问立即变为 `404`。

面试官追问题（请你先答，我再按代码逐题评价）：

1. 攻击者已登录 Workspace A，猜到了 Workspace B 的 `projectId`，并把请求参数改为 B 的 `workspaceId`。当前读和归档请求各会经过哪些判定？为什么选择返回 `404` 而非 `403`？ 答：请求先从服务端 Session 得到用户身份；ProjectQueryService.get() 先执行 WorkspaceAccessService.requireMember(userId, workspaceId)。攻击者不是 B 的成员，这一步就失败并返回 404。即使绕过这一层，findByIdAndWorkspaceId(projectId, workspaceId) 和 PermissionEvaluator.requireProject() 仍携带 B 的 scope 再校验。返回 404 是为了避免确认“该 Project 在 B 是否存在”以及减少资源枚举信息。
2. 管理员刚把某用户从 Workspace 或 Project 移除，但该用户浏览器仍持有未过期 Session。下一次访问项目时，系统依赖什么重新判定？若未来加入权限缓存，最容易破坏什么？答：若引入权限缓存，最危险的是撤销后仍命中旧的 allow 结果：用户已被移除，却在 TTL 到期前仍能读取或写入项目。这违反“成员移除后项目访问立即失效”的不变量。
因此未来缓存至少要有可靠失效机制，例如成员/角色变更时递增授权版本，使旧缓存键失效；缓存不可用时应回退数据库并保持拒绝优先。
3. 两个部署实例同时收到首次初始化请求。仅靠“先查 `isInitialized()` 再插入”为什么不够？当前代码的行锁、事务和最终状态更新各在防什么？答：“先查 isInitialized()”与后续插入不是一个原子操作。两个并发请求都可能观察到“未初始化”，然后都继续创建首个管理员。
当前 create() 的 @Transactional 保证用户、组织、Workspace、成员、Owner 角色、审计和实例状态要么一起提交，要么一起回滚，不会留半套身份图。
lockAndGetInitializedAt() 对 instance_settings 单例行加锁，串行化两个初始化事务：后来的事务必须等待前者结束。
前者提交后，后者读到已初始化状态并抛 InstanceAlreadyInitializedException；markInitialized(...) == 1 是最终状态写入的断言，防止没有成功标记实例却误报成功。

建议固定按“身份从哪来 → scope 怎样传递 → 失败如何表现 → 哪个测试证明”四步讲



一个值得改进、但现在不应过度设计的点是：**权限查询目前每次请求实时查 MySQL，没有引入“成员版本 + Redis 权限缓存”。**  
这会增加授权查询次数，但对 P1 的正确性反而很友好：成员移除后无需等待缓存失效，下一请求即依据数据库事实拒绝。等到有真实的项目量、权限读热点和指标证明需要时，再做带版本号/撤销失效策略的缓存；现在先上分布式缓存、消息失效与回填机制，会把 P1 的“撤销立即生效”风险面扩大很多。
