## 我理解的核心设计
- 关键不变量：密码模型锁定
- 事务/一致性边界：
  唯一事务边界是 InstanceBootstrapService.initialize()。
  事务内顺序：
  1. SELECT ... FOR UPDATE 锁定 instance_settings(id=1)。
  2. 检查 initialized_at；非空立即返回稳定冲突错误。
  3. 插入用户。
  4. 插入 Organization。
  5. 插入 Workspace。
  6. 插入 Workspace Membership。
  7. 建立/读取系统 OWNER 角色并分配。
  8. 写入脱敏初始化审计记录。
  9. 最后设置 initialized_at、默认 Organization 和版本号。
  10. 提交后才返回成功。
任何一步失败都会回滚全部数据。并发请求中，第二个请求必须等待单例行锁；第一个提交后，第二个重新读取到 initialized_at，返回 409 INSTANCE_ALREADY_INITIALIZED。

## 3 个复盘问题
1. 为什么必须锁定 instance_settings 单例行，而不能先查询 users 是否为空？两个事务可能同时看到空表，而且用户数据缺失不等价于实例未初始化。
2. 为什么唯一约束仍然不能替代应用层的初始化检查和稳定 409 错误？数据库唯一约束负责阻止重复事实，应用检查负责提供清楚、稳定的业务错误，两者不能互相替代。
3. BCrypt 为什么每次生成不同 Hash 仍能验证同一个密码，以及 72-byte 上限为什么必须在哈希前检查？ 密码hash是由 密码 + 版本 + cost + salt = hash，系统会用已保存的 hash中解析出 版本、cost、salt，再用用户输入的密码计算，结果相同则正确。因为 BCrypt 的密码输入上限是 72 bytes，超过上限直接返回错误，因为很多BCrypt实现会忽略超过72 bytes的部分 。
