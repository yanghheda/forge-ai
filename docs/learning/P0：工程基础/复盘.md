## 1. 一条真实请求链路

当前最完整的真实链路是 `GET /actuator/health`。它是运维入口，不是业务入口。

```text
HTTP GET /actuator/health
  ↓
RequestIdFilter.doFilterInternal()
  ↓
Spring Actuator HealthEndpoint
  ├─ DataSource HealthContributor → MySQL 连接检查
  ├─ RedisHealthIndicator → Redis PING
  ├─ QdrantHealthIndicator.health()
  │    └─ HttpClient.send(GET qdrant/readyz)
  └─ AgentHealthIndicator.health()
       ├─ AgentServiceTokenProvider.createToken()
       └─ HttpClient.send(GET forge-agent/internal/v1/health/ready)
            └─ require_internal_credential()
                 └─ readiness()
```

具体代码：

- 请求首先经过 [`RequestIdFilter.doFilterInternal()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/platform/web/RequestIdFilter.java:37)，生成或验证 requestId。
- Actuator 自动装配的 MySQL、Redis HealthContributor 根据 [`application.yml`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/resources/application.yml:4) 中的数据源和 Redis 配置进行连接检查。
- [`QdrantHealthIndicator.health()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/platform/health/QdrantHealthIndicator.java:37) 请求 Qdrant `/readyz`。
- [`AgentHealthIndicator.health()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/platform/health/AgentHealthIndicator.java:45)：
  - 调用 [`AgentServiceTokenProvider.createToken()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/platform/agent/AgentServiceTokenProvider.java:42) 签发短时 JWT；
  - 请求 Agent 的 `/internal/v1/health/ready`。
- Agent 侧先执行 [`require_internal_credential()`](/Users/ruicheng/Documents/code/forge-ai/forge-agent/src/forge_agent/api/auth.py:22)，验证算法、issuer、audience、subject、签发和过期时间；
- 最后进入 [`readiness()`](/Users/ruicheng/Documents/code/forge-ai/forge-agent/src/forge_agent/api/health.py:34)。

一个重要区别：Compose 的容器健康检查访问 `/actuator/health/readiness`，而 readiness group 当前只包含 `readinessState,db,redis`。所以 MySQL/Redis 决定 Server 是否接流量；Qdrant/Agent 是完整健康信息中的可降级组件。

公开的 `/api/v1/system/status` 则只有：

[`SystemController.getStatus()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/system/controller/SystemController.java:30) → [`SystemStatusQuery.getStatus()`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/system/application/SystemStatusQuery.java:9)

它返回固定值，没有访问数据库。面试时应主动说明这一点，不要把它讲成业务闭环。

## 2. P0 最重要的三个不变量

### ① 模块只能沿既定方向依赖

不变量：

- Controller 不能直接访问 Repository；
- Application 不能反向依赖 Controller/Infrastructure；
- Domain 不依赖 Spring 等框架；
- 跨 Feature/模块只能通过公开边界访问。

保护证据：

- Server 的 [`ModuleArchitectureTest`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/test/java/ai/forge/server/architecture/ModuleArchitectureTest.java:19) 同时检查层次、跨模块 Repository 和 Swagger 注解位置。
- 其中还有故意违规的 fixture，证明规则真的能够失败，而不只是“对当前代码恰好通过”。
- Web 由 [`eslint.config.mjs`](/Users/ruicheng/Documents/code/forge-ai/forge-web/eslint.config.mjs:5) 禁止 Feature 深层导入，并由 [`check-boundaries.mjs`](/Users/ruicheng/Documents/code/forge-ai/forge-web/tests/module-boundaries/check-boundaries.mjs:3) 做负向验证。

### ② 契约必须是可执行的安全边界

每个 Tool 必须明确权限、风险等级、幂等性、超时、重试、敏感字段和后端映射；Skill 不得引用不存在的 Tool。

保护证据：

- [`tool-contract.schema.json`](/Users/ruicheng/Documents/code/forge-ai/packages/forge-contracts/schemas/tool-contract.schema.json:7) 固定必填安全属性，并限制内部路径、超时和重试范围。
- [`validate_contracts()`](/Users/ruicheng/Documents/code/forge-ai/forge-agent/src/forge_agent/contracts/validator.py:27) 同时校验 JSON Schema 和 Skill→Tool 引用。
- [`test_contract_validation.py`](/Users/ruicheng/Documents/code/forge-ai/forge-agent/tests/contracts/test_contract_validation.py:17) 证明缺少 `risk_level`、引用未知 Tool 都会失败。
- `make ci` 通过 [`contracts-check`](/Users/ruicheng/Documents/code/forge-ai/Makefile:23) 阻断错误契约。

### ③ 部署环境不能改变核心拓扑和数据角色

不变量：

- Web 是唯一宿主机入口；
- Server/Agent/MySQL/Redis/Qdrant 留在内部网络；
- Agent 不获得数据库、GitLab 或部署凭据；
- MySQL 使用持久卷，Redis 明确可丢失；
- 新环境必须经过同一组构建、迁移和 Smoke 门禁。

保护证据：

- [`compose.yml`](/Users/ruicheng/Documents/code/forge-ai/deploy/compose.yml:31) 固定网络、环境变量、健康检查和数据卷。
- [`infrastructure-compose.sh`](/Users/ruicheng/Documents/code/forge-ai/tests/infrastructure-compose.sh:31) 会解析最终 Compose，而不是仅 grep 原始 YAML；它检查唯一入口、内部网络、禁止端口和 Agent 禁止凭据。
- [`InfrastructureConnectivityIntegrationTest`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/test/java/ai/forge/server/infrastructure/InfrastructureConnectivityIntegrationTest.java:21) 验证实际连接的是 MySQL 8 和 Redis。
- [`FlywayMigrationIntegrationTest`](/Users/ruicheng/Documents/code/forge-ai/forge-server/src/test/java/ai/forge/server/infrastructure/FlywayMigrationIntegrationTest.java:34) 验证空库迁移、单例约束、重复执行和 checksum。
- [`three-app-smoke.sh`](/Users/ruicheng/Documents/code/forge-ai/tests/three-app-smoke.sh:14) 验证 Web→Server→Agent，以及 Agent 拒绝无效凭据。

## 3. 给你的三个面试追问

先不提供参考答案。请分别按“现象 → 是否影响接流量 → 数据是否正确 → 定位证据 → 恢复办法”回答。

1. **依赖故障**

   MySQL 正常，Redis 完全不可达，同时 Qdrant 也宕机。面试官问：`/actuator/health/readiness` 和完整 `/actuator/health` 应分别表现为什么？Server 是否还应该接收新流量？为什么 Redis 和 Qdrant 的处理不同？
   1. Redis 故障后 readiness 为 DOWN，实例应停止接收新流量。完整 health 也会因为 Redis 的 DOWN 聚合为 DOWN；Qdrant 自身是 DEGRADED，但其优先级低于 DOWN。Redis 虽然不是业务事实来源，却是当前运行所需的会话基础设施；Qdrant 是可重建的派生索引，因此只降级搜索能力，不应阻断基础业务。
2. **内部接口攻击**

   攻击者可以连到 Agent 的 `/internal/v1/health/ready`，依次使用：无 Token、伪造 HS256 Token、错误 audience、过期 Token，以及刚刚窃取但仍在有效期内的真实 Token。哪些请求会被拒绝？现有实现还留下什么风险？你会如何判断风险是否需要现在修复？
   1. 签名解决“谁签发的”，claims 解决“签给谁、何时有效”，但 bearer JWT 本身不解决有效期内重放。
3. **供应链/契约绕过**

   有人提交一个 Skill，引用不存在的 Tool；又提交一个 Tool，但删除 `risk_level`，同时试图让 Backend 映射到公开 `/api/v1/...`。这次提交会在哪些层次失败？如果只运行应用单元测试、不运行 `make ci`，有什么可能漏过？
   1. JSON Schema 检查单份文档的结构和字段约束；自定义 validator 检查跨文档语义；CI 保证两者不会被开发者遗漏。

## 4. 值得改进、但现在不应过度设计的点

实际 OpenAPI Client 生成尚未落地。

[`GeneratedApiClient`](/Users/ruicheng/Documents/code/forge-ai/forge-web/src/lib/api/generated/client.ts:3) 目前只是 transport 包装；[`ProjectOverviewSummary`](/Users/ruicheng/Documents/code/forge-ai/forge-web/src/features/project/api/project-overview-api.ts:7) 仍是手写 DTO，并手动从 `unknown` 解析字段。因此“Server OpenAPI 是前端类型事实来源”目前更多是接入点设计，而不是已经由流水线保护的不变量。

这确实值得后续改进，但不应在 P0 继续搭复杂生成平台，依据是：

- 会话 04 明确要求的是“生成 Client 占位”；
- 当前只有一个固定状态接口，自动生成带来的即时收益很低；
- 身份、错误模型和业务 DTO 会在 P1/P2 快速变化；
- 现在更合适的是保留稳定 transport 注入边界，等出现第一个真实业务纵向切片时，再加入确定版本的生成器、生成命令和 drift check。
