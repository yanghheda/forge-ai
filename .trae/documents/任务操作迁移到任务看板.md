# 任务操作迁移到任务看板（实施方案）

## 一、背景与目标

当前 UX/开发/测试任务（`UX_TASK`/`DEV_TASK`/`QA_TASK`）的创建与流转分散在需求详情的角色工作区（[stage-tasks.tsx](file:///Users/ruicheng/Documents/code/forge-ai/forge-web/src/features/work-item/components/stage-tasks.tsx)）以及开发工作区里，和需求级流转混在一起，操作入口不集中。用户已确认改造方向：

- **任务看板 = 任务操作面**：领域负责人在看板创建任务，执行人在看板流转任务状态。
- **需求详情 = 材料 + 需求决策面**：任务完成后回到需求详情做需求级流转。
- 角色工作区**彻底移除任务区**，只保留材料。

本次范围只含 UX/DEV/QA 任务；缺陷（BUG）保持现有 `/defects` 页与开发工作区缺陷面板，不在迁移范围。

## 二、边界口径（已确认）

| 事项 | 结论 |
|---|---|
| 跨泳道拖拽 | **不做**状态流转。看板 lane 必须等于任务真实 status（`ConsoleService.move` 已强制），拖拽仅保留同列排序；跨列提示改为"看板排序不改变任务状态，请使用卡片上的状态操作" |
| 任务流转 | 一律走 `POST /v1/work-items/{id}/transitions`（action + expectedVersion + idempotencyKey + reason）；DEV_TASK 的 `START` 仍走 `startDevelopment`、`SUBMIT_REVIEW` 仍走 `completeDevTask` |
| 创建工作区任务列表 | 彻底移除 `StageTasks`（`/requirements/:id/ux\|dev\|qa` 三处） |
| 开发工作区 | 移除"启动开发""提交验证"两个任务流转按钮；保留 Dev Task 交付链路展示、"触发 Pipeline""查看 MR"（材料/交付操作，不改任务状态） |
| 需求级流转 | 保持在需求详情页 `RequirementWorkflowControls`，不改 |
| 权限/守卫 | 服务端仍是唯一权威；看板只做"可执行动作"的可见性投影 |

## 三、服务端改动（forge-server）

### 1. 批量读取工作项（消除 N+1）

- [WorkItemStore.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/workitem/application/WorkItemStore.java)：新增 `List<WorkItem> findByIdsAndScope(long organizationId, List<Long> workItemIds)`。
- WorkItemMapper（`@Select` + `<foreach>`，必须带 `organization_id` 与 `deleted_at IS NULL`）与 `MybatisWorkItemStore` 实现；空集合直接返回 `List.of()`。

### 2. 看板卡片携带可执行动作

- [ConsoleModels.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/console/application/ConsoleModels.java)：`BoardItem` 增 `List<WorkflowAction> availableActions`、`Map<WorkflowAction, List<String>> guardHints`（与 `WorkItemDetailResponse` 契约一致）；新增 record `ExecutorOption(long userId, String displayName)` 与 `TaskCreationOption(long requirementId, String requirementItemKey, String requirementTitle, WorkItemType taskType, List<ExecutorOption> executors)`。字段逐个补中文块注释。
- [ConsoleService.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/console/application/ConsoleService.java)：`board(userId)` 先批量取 WorkItem，仅对 `UX_TASK/DEV_TASK/QA_TASK` 调 `transitionService.hints(userId, item)`；BUG 返回空。
  - 可行性已核实：任务类型在注册表中只有 `reasonGuard`，`policy.canAct/missing` 只依赖「需求内角色事实 + 需求状态 + assignee 是否为当前用户」，因此可用 `(type, status, requirementId, assignee==userId)` 做请求内记忆化，避免逐卡重复计算。

### 3. 创建入口数据源

- 新增 `GET /v1/task-board/creation-options`（[ConsoleController.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/console/controller/ConsoleController.java) → `ConsoleService.taskCreationOptions(userId)` → `ConsoleStore`/`ConsoleMapper`）。
- SQL 一条完成：`work_items`（`REQUIREMENT`、未删除、`status IN ('READY_FOR_UX','READY_FOR_DEV','READY_FOR_QA')`）内连 `requirement_participants`（`user_id=#{userId}`）并按状态限定角色（`READY_FOR_UX→UX`、`READY_FOR_DEV→DEVELOPER`、`READY_FOR_QA→QA`，与 `DeliveryWorkflowPolicy.requireCreation` 一致），左连 `requirement_executors` + `users` 取该角色已关联执行人。
- **必须复刻** `DeliveryWorkflowMapper.isLeader/isExecutor` 的语义：`organization_members.status='ACTIVE'`、`users.status='ACTIVE'`、leader 要求 `roles.code=CONCAT(role,'_ADMIN')`、executor 要求 `roles.code IN (role, CONCAT(role,'_ADMIN'))`。
- Service 层再用 `hasOrganizationPermission(userId, organizationId, taskType.permissionResource()+".create")` 过滤（ADR-026：QA_TASK→`qa.*`，其余按类型）。
- 任务类型由需求状态唯一决定，前端不需要再选类型。

## 七、风险与遗留

1. **DEV_TASK 提交验证缺少前置可见性**：Pipeline/MR 事实只在开发工作区，看板只能等 `completeDevTask` 失败后给出服务端错误。本次保持与旧 `StageTasks` 同等能力，后续如需可在看板补充 dev summary 摘要（遗留项）。
2. **创建选项与权威守卫不一致的风险**：SQL 必须复刻 `isLeader/isExecutor`（ACTIVE 成员、角色码）语义，用"撤权后不返回"用例锁定。
3. **hints 计算成本**：已用批量查询 + 记忆化 + BUG 跳过控制；若未来工作项规模上升，再给看板加分页上限。
4. **双创建入口遗留**：`/v1/development/requirements/{id}/tasks`（`createDevTask`）仍存在但已无前端调用，记为遗留项，不在本次删除。
5. **缓存失效**：动作只保证 invalidate `["task-board"]` 与创建选项；需求阶段变化依赖 TanStack Query 导航重取。
