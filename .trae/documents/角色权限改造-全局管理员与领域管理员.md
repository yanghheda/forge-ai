# 角色权限改造：全局管理员与领域管理员

## 1. 目标与范围

### 本次要做

1. `ADMIN` 语义升级为**全局管理员**（仅改展示名与描述，保留 `roles.code='ADMIN'`），权限与 `OWNER` 并列，是唯一可管理成员并分配领域管理员的管理角色。
2. 新增 4 个**领域管理员**系统角色：`PRODUCT_ADMIN`（产品管理员）、`UX_ADMIN`（UX 管理员）、`DEVELOPER_ADMIN`（开发管理员）、`QA_ADMIN`（测试管理员）。
3. 注册可选角色调整为：`ADMIN` / `PRODUCT` / `UX` / `DEVELOPER` / `QA` 五选一；四个领域管理员**不可自助注册**，只能由全局管理员或 Owner 在成员管理中分配。
4. 删除 `RELEASE_APPROVER`（发布审批）系统角色，其审批职责移交**开发管理员 + 全局管理员 + Owner**。
5. 领域管理员成为对应模块的可编辑角色（产品管理员可编辑 PRD、开发管理员可编辑开发与发布等），使领域管理员天然成为阶段负责人。
6. 新增两个**审核权限码** `requirement.approve`（需求审核）与 `ux.approve`（UX 审核），**只授予对应的领域管理员**（`PRODUCT_ADMIN` / `UX_ADMIN`）以及 `ADMIN` / `OWNER`，为后续需求状态机追加“需求审核 / UX 审核”阶段预留授权。

### 本次明确不做（动机已在需求中说明，留待后续阶段）

* 需求与各领域管理员的关联、领域管理员向下分配工作人员、按阶段创建任务、领域管理员对下属的审批动作。

* 需求状态机新增“需求审核 / UX 审核”状态与流转动作，以及把现有 `APPROVE_PRODUCT_REVIEW` / `APPROVE_UX_REVIEW` 切到新权限码：本次**只建码与授权**，新码暂不被任何 `TransitionDefinition` 引用。

* 需求参与人（`RequirementParticipantRole`）选择逻辑**不改**：本阶段领域管理员不会出现在需求参与人下拉里，这是已知的阶段性限制。

* 领域管理员暂不获得 `member.read` / `member.manage`，成员治理仍只由 `ADMIN` / `OWNER` 承担。

## 3. 目标权限矩阵

新增角色 id 由 `roles` 自增决定（当前 `AUTO_INCREMENT=8`，删除 `RELEASE_APPROVER` 后新角色取 8–11），迁移中一律用 `code` 关联，不硬编码 id。

| 角色（code）                | 权限集合                                                                    |
| ----------------------- | ----------------------------------------------------------------------- |
| `ADMIN` 全局管理员           | 原有 36 条 + `requirement.approve`、`ux.approve`                            |
| `PRODUCT_ADMIN` 产品管理员   | 等同 `PRODUCT`，另加 `requirement.approve`                                   |
| `UX_ADMIN` UX 管理员       | 等同 `UX`，另加 `ux.approve`                                                 |
| `DEVELOPER_ADMIN` 开发管理员 | `DEVELOPER` ∪ `RELEASE_APPROVER`（额外获得 `approval.decide`、`release.read`） |
| `QA_ADMIN` 测试管理员        | 等同 `QA`                                                                 |

本次新增两个权限码（`permissions` 表当前 `AUTO_INCREMENT=41`，即 id 41/42）：

* `requirement.approve`（resource=`requirement`，action=`approve`）：需求审核；由产品管理员执行，决定需求是否通过审核。

* `ux.approve`（resource=`ux`，action=`approve`）：UX 审核；由 UX 管理员执行，决定体验方案是否通过。

权限码清单（本次涉及）：

* `PRODUCT`：`requirement.read/create/edit/review`、`ux.read`、`task.read/create/edit`、`document.read/create/edit/publish`、`ux.review`、`ux.skip`、`agent.run`、`release.read/manage/precheck/deploy`

* `UX`：`requirement.read`、`ux.read/create/edit/review`、`task.read/create/edit`、`document.read/create/edit/publish`、`agent.run`

* `DEVELOPER`：`requirement.read`、`ux.read`、`task.read/create/edit`、`document.read`、`agent.run`、`repo.read/write`、`development.submit`、`bug.read/edit`、`bug.resolve`、`release.read`

* `QA`：`requirement.read`、`ux.read`、`task.read/create/edit`、`document.read`、`agent.run`、`qa.manage/execute/read`、`bug.read/create/edit/verify`、`release.read/manage/precheck`

* `RELEASE_APPROVER`（待删）：`requirement.read`、`ux.read`、`task.read`、`document.read`、`approval.decide`、`release.read`、`agent.run`

由此得到的重点变化：

* `approval.decide`：`ADMIN`、`DEVELOPER_ADMIN`、`OWNER`（原为 `ADMIN`、`OWNER`、`RELEASE_APPROVER`）

* `repo.write`：`ADMIN`、`DEVELOPER`、`DEVELOPER_ADMIN`、`OWNER`

* `agent.run`：`ADMIN`、`DEVELOPER`、`DEVELOPER_ADMIN`、`OWNER`、`PRODUCT`、`PRODUCT_ADMIN`、`QA`、`QA_ADMIN`、`UX`、`UX_ADMIN`

* `requirement.approve`（新）：`ADMIN`、`OWNER`、`PRODUCT_ADMIN`，`PRODUCT` 不持有

* `ux.approve`（新）：`ADMIN`、`OWNER`、`UX_ADMIN`，`UX` 不持有

## 4. 具体改动

### 4.1 新增迁移 `V7__domain_admin_roles.sql`

新增 `forge-server/src/main/resources/db/migration/V7__domain_admin_roles.sql`。内容与顺序：

1. **改名**：

   ```sql
   UPDATE roles
   SET name = '全局管理员',
       description = '全局管理员；负责成员治理、角色分配与跨领域协调，权限与 Owner 并列但不可管理 Owner'
   WHERE code = 'ADMIN' AND organization_id IS NULL;
   ```

2. **插入 4 个领域管理员**（`organization_id` 为 `NULL`，`system_role=1`，name/description 使用中文并说明业务语义）：

   ```sql
   INSERT INTO roles (organization_id, code, name, system_role, description) VALUES
     (NULL,'PRODUCT_ADMIN','产品管理员',1,'产品领域负责人；拥有产品全部权限，负责产品阶段任务分配与需求审核'),
     (NULL,'UX_ADMIN','UX 管理员',1,'UX 领域负责人；拥有 UX 全部权限，负责体验阶段任务分配与 UX 审核'),
     (NULL,'DEVELOPER_ADMIN','开发管理员',1,'开发领域负责人；拥有研发全部权限并承接发布审批职责'),
     (NULL,'QA_ADMIN','测试管理员',1,'测试领域负责人；拥有测试全部权限，负责测试阶段任务分配与质量结论');
   ```

3. **继承授权**：用 `INSERT ... SELECT` 按 `code` 关联，避免硬编码 id：

   ```sql
   -- 产品 / UX / 测试管理员继承对应基础角色权限
   INSERT INTO role_permissions (role_id, permission_id)
   SELECT admin_role.id, rp.permission_id
   FROM roles admin_role
   JOIN roles base_role
     ON base_role.organization_id IS NULL
    AND base_role.code = CASE admin_role.code
          WHEN 'PRODUCT_ADMIN' THEN 'PRODUCT'
          WHEN 'UX_ADMIN' THEN 'UX'
          WHEN 'QA_ADMIN' THEN 'QA'
        END
   JOIN role_permissions rp ON rp.role_id = base_role.id
   WHERE admin_role.organization_id IS NULL
     AND admin_role.code IN ('PRODUCT_ADMIN','UX_ADMIN','QA_ADMIN');

   -- 开发管理员 = 开发 ∪ 原发布审批
   INSERT INTO role_permissions (role_id, permission_id)
   SELECT admin_role.id, rp.permission_id
   FROM roles admin_role
   JOIN roles base_role
     ON base_role.organization_id IS NULL
    AND base_role.code IN ('DEVELOPER','RELEASE_APPROVER')
   JOIN role_permissions rp ON rp.role_id = base_role.id
   WHERE admin_role.organization_id IS NULL
     AND admin_role.code = 'DEVELOPER_ADMIN';
   ```

4. **新增两个审核权限码并授权**（必须在第 2 步之后，因为要按 `code` 关联到新建的领域管理员；`OWNER` / `ADMIN` 原本持有全部权限，新码需显式补授）：

   ```sql
   INSERT INTO permissions (code, resource, action, description) VALUES
     ('requirement.approve','requirement','approve','由产品管理员执行需求审核，决定需求是否通过审核并进入下一阶段'),
     ('ux.approve','ux','approve','由 UX 管理员执行 UX 审核，决定体验方案是否通过');

   -- OWNER / ADMIN 补齐新码，保持“全部权限”语义
   INSERT INTO role_permissions (role_id, permission_id)
   SELECT r.id, p.id
   FROM roles r
   JOIN permissions p ON p.code IN ('requirement.approve','ux.approve')
   WHERE r.organization_id IS NULL AND r.code IN ('OWNER','ADMIN');

   -- 需求审核只给产品管理员
   INSERT INTO role_permissions (role_id, permission_id)
   SELECT r.id, p.id
   FROM roles r
   JOIN permissions p ON p.code = 'requirement.approve'
   WHERE r.organization_id IS NULL AND r.code = 'PRODUCT_ADMIN';

   -- UX 审核只给 UX 管理员
   INSERT INTO role_permissions (role_id, permission_id)
   SELECT r.id, p.id
   FROM roles r
   JOIN permissions p ON p.code = 'ux.approve'
   WHERE r.organization_id IS NULL AND r.code = 'UX_ADMIN';
   ```

5. **删除** **`RELEASE_APPROVER`**（先清关联表，再删角色；全部限定 `organization_id IS NULL` 以免误伤公司自定义角色）：

   ```sql
   DELETE mr FROM member_roles mr
     JOIN roles r ON r.id = mr.role_id
     WHERE r.code = 'RELEASE_APPROVER' AND r.organization_id IS NULL;

   DELETE rp FROM role_permissions rp
     JOIN roles r ON r.id = rp.role_id
     WHERE r.code = 'RELEASE_APPROVER' AND r.organization_id IS NULL;

   DELETE FROM roles WHERE code = 'RELEASE_APPROVER' AND organization_id IS NULL;
   ```

> `V1` / `V3` 为已发布迁移，**不得回改**；`RELEASE_APPROVER` 的清理与 `ADMIN` 改名全部由 `V7` 前进式完成。

## 5. 假设与决策

1. **保留** **`ADMIN`** **代码**，仅改展示名与描述；4 个新角色代码为 `PRODUCT_ADMIN` / `UX_ADMIN` / `DEVELOPER_ADMIN` / `QA_ADMIN`（用户已确认）。
2. **“权限仅次于 Owner”的落地方式**：`ADMIN` 权限集合与 `OWNER` 相同，差异体现在 Owner 不可被分配或降级（`deleteAssignableRoles` 排除 `OWNER`、`UpdateMemberRequest` 不接受 `OWNER`），全局管理员只能治理非 Owner 成员。不额外裁剪 `ADMIN` 权限，因为当前 `permissions` 表中没有可专属 Owner 的审计 / 配置权限。
3. **领域管理员权限 = 对应基础角色权限**（开发管理员额外承接原发布审批角色的权限集合），本阶段不授予 `member.read` / `member.manage`；下属管理与下属审批留待后续工作流阶段。
4. **审核权限归属**（用户已确认）：需求审核与 UX 审核只由对应领域管理员执行，因此新增独立的 `requirement.approve` / `ux.approve`，**不授予** `PRODUCT` / `UX` 基础角色；现有 `requirement.review` / `ux.review` 及其流转保持原样。
5. **新审核码本次仅建码与授权**：暂不被任何 `TransitionDefinition` 引用，等后续需求状态机追加“需求审核 / UX 审核”阶段时再接入。
6. **注册仍为 PENDING 审核制**：以 `ADMIN` 注册的账号同样需要现有全局管理员或 Owner 审核启用。
7. **`RELEASE_APPROVER`** **的权限不整体迁移**：只把 `approval.decide` 与 `release.read` 随“开发管理员 = 开发 ∪ 发布审批”并入；`release.deploy` 等原本就未授予该角色，保持原矩阵不动。
8. 需求参与人下拉（[organization-requirement-detail.tsx#L193](file:///Users/ruicheng/Documents/code/forge-ai/forge-web/src/features/work-item/components/organization-requirement-detail.tsx#L193)）本阶段不改，领域管理员暂不可被选为需求参与人。
