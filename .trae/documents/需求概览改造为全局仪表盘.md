# 需求概览 → 全局仪表盘（需求数据大屏）

## 一、背景与目标

`/overview` 当前的「需求概览」实际是「一个需求列表 + 几个数字卡片」，其中列表与「任务看板」的数据完全重合，页面没有提供额外的决策信息。

本次把它改造为**只读的全局仪表盘**：以需求分布、趋势、质量风险为主，回答「交付链路卡在哪、吞吐在变好还是变差、哪些需求有风险」这三个问题，彻底不再承担列表职责。

已确认的四项决策：

| 决策点 | 结论 |
|---|---|
| 页面定位 | 纯只读大屏，需求列表移走；仅保留「新建需求」入口 |
| 图表方案 | 引入 ECharts（按需引入，`echarts/core`） |
| 数据来源 | 后端新增专用聚合接口，前端只负责渲染 |
| 首期模块 | L1 核心指标条 + L2 状态漏斗/优先级分布 + L3 趋势 + L4 质量风险（**不含 Agent 动态**） |

### 范围决策（已确认）

1. **不新建 `/requirements` 全量列表页。** 任务看板已经覆盖全量工作项浏览，新建列表页会把刚消除的重合重新引入。首期保持「我的需求」作为唯一列表入口，全量浏览继续走任务看板。
2. **保持浅色主题。** 现有设计系统（`forge-web/src/app/globals.css`）是浅色 token，做成深色大屏会与 App Shell 割裂。本次用「密集网格 + 图表」的大屏布局，配色沿用 `--forge-*` token。
3. **不保留旧的 `/v1/dashboard/overview` 链路**，落地后按「删除已死代码」一节整体移除。

## 二、后端设计（forge-server）

归属 **workitem 模块**：所有指标都是需求交付视角，且 `RequirementController` 已经承载 `/api/v1/requirements/overview`，前端页面也属于 `work-item` feature。不放进 `console` 模块，避免继续膨胀控制台职责。

分层与 `ConsoleService` / `RequirementController` 现有模式保持一致：Controller → Service → Store 接口 → `@Mapper`（内联 `@Select`、显式 `organization_id` 条件）。

可空字段用 `null` 表达「无样本」，不用 0 冒充：`onTimeRate`（窗口内无带 `due_at` 的完成样本）、`avgCycleDays`、`createdDeltaRate` / `completedDeltaRate`（上期为 0 时）。

### 关键 SQL 口径

- **状态分布 / 优先级分布**：`work_items`，`type='REQUIREMENT' AND deleted_at IS NULL`，`GROUP BY status` / `GROUP BY priority`。状态序列由 Service 按 `WorkItemStatus` 流程顺序补齐（含 `CANCELLED` / `REJECTED`）。
- **每日完成量（精确）**：**用 `work_item_events` 而不是 `updated_at`**。取每个需求首次进入终态的时点，避免 `RELEASED → DONE` 被重复计数：

  ```sql
  SELECT DATE(first_done) day, COUNT(*) total FROM (
    SELECT e.work_item_id, MIN(e.created_at) first_done
    FROM work_item_events e JOIN work_items wi ON wi.id = e.work_item_id
    WHERE e.organization_id = #{organizationId} AND wi.type = 'REQUIREMENT' AND wi.deleted_at IS NULL
      AND e.to_status IN ('DONE', 'RELEASED')
    GROUP BY e.work_item_id
  ) t WHERE first_done >= UTC_DATE() - INTERVAL #{days} DAY GROUP BY DATE(first_done)
  ```

  现有 `ConsoleMapper.trend()` 用 `updated_at`，语义不准确；本接口不复用该口径。
- **每日新增**：`work_items.created_at` 按 `DATE()` 分组。
- **完成质量指标**（一条聚合 SQL 同时返回）：窗口内完成的需求中 `completedInRange`、`onTimeTotal`（设置了 `due_at`）、`onTimeOk`（`first_done <= due_at`）、`avgCycleDays = AVG(TIMESTAMPDIFF(HOUR, created_at, first_done)) / 24`。
- **超期**：`due_at IS NOT NULL AND due_at < UTC_TIMESTAMP(6)` 且状态不在 `DONE/RELEASED/CANCELLED/REJECTED`。
- **存量（燃尽）**：一条 baseline 查询取「窗口开始前已创建、且窗口开始前未完成」的数量，再由 Service 用 `baseline + 累计新增 - 累计完成` 递推每日存量。
- **Bug 分布**：`work_items`，`type='BUG' AND deleted_at IS NULL`，`GROUP BY severity, status`。取**当前快照**（不加时间窗），用于看当前质量状况。
- **QA 通过率**：`test_results` JOIN `test_runs`，按 `test_runs.started_at` 落窗口；`passRate = passed / (passed + failed + blocked)`。
- **风险清单**：状态未终结且（超期 或 `blocked_at IS NOT NULL`）的 Top N，`ORDER BY (blocked_at IS NOT NULL) DESC, due_at ASC`。

### 已知限制（需在 UI 文案上如实标注）

- **`blocked_at` 目前恒为空**：`V1__company_platform_baseline.sql` 中该字段注释为「本轮不开放写入」。风险清单首期实际以「超期」为主，阻塞维度是预留。UI 不显示空阻塞分区。
- **`work_item_events` 无 `(organization_id, to_status, created_at)` 复合索引**，当前只有 `fk_work_item_events_organization`。数据量小可接受；若需要，后续以新的 Flyway 迁移（V7，`ALTER TABLE ... ADD INDEX`）补索引，不回改历史脚本。
- **平均交付周期是 `created_at → 首次进入终态`**，不是「实际开发工时」，UI 标注为「按状态流转估算」。

### 删除已死代码

`/api/v1/dashboard/overview` 整条链路在新页面落地后**没有任何调用方**（已全仓确认，仅 `requirement-dashboard.tsx` 引用）：

- 删除 `ConsoleController.dashboard()`、`ConsoleService.dashboard()`、`ConsoleModels.Dashboard` / `TrendPoint`
- 删除 `ConsoleStore` + `ConsoleMapper` 的 `weeklyDeliveries` / `activeAgents` / `personalTodos` / `stages` / `trend`
- 删除前端 `console-api.ts` 的 `DashboardOverview` / `getDashboardOverview` 及其 `index.ts` 导出

## 三、前端设计（forge-web）

### ECharts 接入

- `npm install echarts`（写入 `forge-web/package.json` dependencies，lock 文件为 `package-lock.json`）。
- **不引入 `echarts-for-react`**（对 React 19 支持滞后）。新增本地薄封装 `forge-web/src/features/work-item/components/echart.tsx`：
  - `"use client"`，在 `useEffect` 内 `await import("echarts/core")` 并注册 `BarChart / LineChart / PieChart / FunnelChart` 与 `GridComponent / TooltipComponent / LegendComponent`，保持按需打包与 SSR 安全；
  - 用 `ResizeObserver` 响应容器尺寸，卸载时 `dispose()`；
  - 单一 `option` prop 驱动。
- **主题取值**：新增 `forge-web/src/features/work-item/utils/echarts-theme.ts`，用 `getComputedStyle(document.documentElement).getPropertyValue("--forge-…")` 读取 `globals.css` 的 token 组装调色板，避免在 TS 里硬编码第二套颜色。
- **vitest 兼容**：jsdom 无 canvas，仪表盘测试中 `vi.mock("./echart")` 成占位元素，断言围绕 KPI 数字与卡片标题，不碰 canvas。

### 页面布局（4 行密集网格）

```
┌ 头部：全局仪表盘 + 时间范围切换(7/30/90天) + 新建需求 ─────────────┐
├ KPI ×6：总量 / 进行中 / 已完成 / 超期 / 按时交付率 / 平均交付周期 ┤

└ Bug severity×status(堆叠条形)     │ QA 通过率(环形) │ 风险预警清单 ┘
```

## 四、验证方式

1. **后端集成测试**（新增 `forge-server/src/test/java/ai/forge/server/workitem/RequirementAnalyticsIntegrationTest.java`）
   沿用 `WorkItemIntegrationTest` 的写法：`extends InfrastructureIntegrationTestBase` + `TestRestTemplate`（真实 Session/CSRF）+ `JdbcTemplate` 搭建事实。至少覆盖：
   - 空公司返回全 0 且 `onTimeRate` / `avgCycleDays` 为 `null`；
   - 造若干需求与 `work_item_events`，断言 `statusFunnel`、`flowTrend`、`backlogTrend` 的数值；
   - `RELEASED → DONE` 的需求在完成趋势中**只计一次**；
   - 跨公司数据不出现在结果里（租户隔离）；
   - `range` 越界（如 `0` / `999`）返回 400。
   > 集成测试需要本机 MySQL，先起基础设施。
2. **前端单元测试**：`my-requirements` 保留原列表与创建抽屉断言；新增 `requirement-analytics-dashboard.test.tsx` 断言 6 个 KPI、4 类图表卡片标题、风险清单渲染，以及 `range` 切换触发新查询。

4. **人工验证**：`npm run dev` 起 forge-web，登录后访问 `/overview` 确认四个分区渲染与响应式收缩；访问 `/my-requirements` 确认列表未回归；访问 `/task-board` 确认未受影响。
