# 系统设置菜单按角色控制可见性

## 摘要

为 AppShell 侧边栏的「系统设置」分组（成员管理 `/settings/members`、集成设置 `/settings/integrations`）增加可见性判定：仅当前用户角色包含 `OWNER` 或 `ADMIN` 时渲染该分组；其他角色（含领域管理员）不渲染分组标题与两个入口。

## 现状分析

- 菜单在 [app-shell.tsx](file:///Users/ruicheng/Documents/code/forge-ai/forge-web/src/components/app-shell/app-shell.tsx#L158-L170) 中无条件渲染：`系统设置` 标签 + 两个 `Link`。
- 现成的同类先例：`待审批` 入口通过 [canDecideApprovals](file:///Users/ruicheng/Documents/code/forge-ai/forge-web/src/components/app-shell/app-shell.tsx#L263-L269) 按角色集合 `APPROVAL_DECISION_ROLES = ["OWNER", "ADMIN", "DEVELOPER_ADMIN"]` 控制显隐，注释明确「与服务端授权范围保持一致」。
- 前端角色来源：`getCurrentUser()`（`/v1/me`）返回 `organization.roles: string[]`，不返回权限码；`AppShell` 已通过 `useQuery(["current-user"])` 拿到它。
- 服务端权限事实（已验证迁移脚本）：
  - 成员管理走 `member.manage`（[OrganizationMemberService.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/organization/application/OrganizationMemberService.java#L68)），集成设置走 `integration.manage`（[GitLabConnectionService.java](file:///Users/ruicheng/Documents/code/forge-ai/forge-server/src/main/java/ai/forge/server/gitlab/application/GitLabConnectionService.java#L45)）。
  - `member.read` / `member.manage` / `integration.manage` 在 V1 基线中只授予 `OWNER`（role 1）与 `ADMIN`（role 2）；V2–V11 没有任何迁移给其他角色补授这三个码（已逐脚本核对）。ADR-026 也明确 Owner/Admin 收敛后「只保留成员治理、外部集成……」。
- 结论：按角色 `["OWNER", "ADMIN"]` 判定与后端权限码持有者完全一致，不会产生「前端可点、后端拒绝」的错配；现有 `canEditModule`、`canDecideApprovals` 均采用同样口径。

## 变更方案

### 1. `forge-web/src/components/app-shell/app-shell.tsx`

1) 在 `showApprovals` 之后新增判定（复用同一 `currentUser` 查询）：

```tsx
/* 仅持有成员治理与集成管理权限的角色看到「系统设置」入口，与服务端 member.manage / integration.manage 的授权范围保持一致。 */
const showSystemSettings = canManageSystemSettings(currentUser.data?.organization.roles);
```

2) 用条件包裹整个「系统设置」分组（标签 + 两个 Link），避免出现无子项的空标题：

```tsx
{showSystemSettings && (
  <>
    <p className={styles.navLabel}>{navigationCollapsed ? "" : "系统设置"}</p>
    <Link to="/settings/members" …>…成员管理…</Link>
    <Link to="/settings/integrations" …>…集成设置…</Link>
  </>
)}
```

（标签、Link 的 className、图标、收起态文案保持原样不动。）

3) 在文件底部、`canDecideApprovals` 附近新增常量与函数，风格与既有判定一致：

```tsx
/* 拥有「系统设置」入口可见性的角色集合，与服务端 member.manage 与 integration.manage 的授权范围保持一致。 */
const SYSTEM_SETTINGS_ROLES = ["OWNER", "ADMIN"];

/* 判断当前用户角色是否应展示「系统设置」菜单分组。 */
function canManageSystemSettings(roles?: string[]): boolean {
  return Boolean(roles?.some((role) => SYSTEM_SETTINGS_ROLES.includes(role)));
}
```

### 2. `forge-web/src/components/app-shell/app-shell.test.tsx`

在同一文件内新增小型桩函数，供新用例覆写角色（`beforeEach` 中默认仍是 `["OWNER"]`，现有断言不受影响）：

```tsx
/* 覆写当前用户替身与 react-query 缓存，用于按角色验证菜单可见性。 */
function stubCurrentUser(roles: string[]) {
  const user = { id: 1, email: "yang@example.com", displayName: "杨佳锡", organization: { id: 2, slug: "forge", name: "Forge", roles } };
  authApi.getCurrentUser.mockResolvedValue(user);
  testQueryClient.setQueryData(["current-user"], user);
}
```

新增 3 个用例：
- `Owner 看到系统设置分组`：默认 OWNER，断言 `系统设置` 文本存在，`成员管理` 链接 `href="/settings/members"`、`集成设置` 链接 `href="/settings/integrations"`。
- `全局管理员看到系统设置分组`：`stubCurrentUser(["ADMIN"])` 后断言同上（至少断言两个链接存在）。
- `非 Owner/Admin 角色隐藏系统设置分组`：`stubCurrentUser(["PRODUCT"])` 后断言 `queryByText("系统设置")`、成员管理、集成设置均不存在，且 `需求列表` 等其他导航仍存在。

## 假设与决策

- 判定方式沿用仓库既有前端口径：按角色集合判定（与后端权限码持有者一致），不改动 `/v1/me` 返回结构，不新增权限码相关接口改动。
- 分组标题 `系统设置` 与两个入口同生同灭：两个入口都不可见时隐藏标题，避免空分组标题残留（与现有 `Agent` 分组仅按条件追加单项的观感一致）。
- 不做路由级拦截：本次只按用户要求控制「菜单显示」；直接输入 URL 访问 `/settings/members` 等页面时，服务端 `member.manage` / `integration.manage` 仍会按既有逻辑拒绝（页面展示错误提示），该行为不在本次范围。
- 不涉及权限模型、认证或事务边界变更，无需新增 ADR；设计文档（PAGE-MAP 等）无需修改。
- 领域管理员（`PRODUCT_ADMIN`、`UX_ADMIN`、`DEVELOPER_ADMIN`、`QA_ADMIN`）按用户要求不显示该分组（其权限码集合中也不含 `member.manage` / `integration.manage`）。
